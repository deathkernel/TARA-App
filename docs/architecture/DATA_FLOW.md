# TARA Canonical Data Flow

**Status:** Proposed target behavior

## 1. One authoritative path

All interfaces must enter the same application request boundary. No UI, CLI, workflow, or integration may bypass application coordination and invoke an adapter directly.

~~~mermaid
sequenceDiagram
    participant U as User
    participant I as Interface
    participant A as Application
    participant W as Workflow Coordinator
    participant P as Policy / Approval
    participant X as Execution
    participant D as Operation Adapter
    participant S as State Store
    participant L as Audit

    U->>I: Submit request
    I->>A: Validated transport request
    A->>S: Create request/session state
    A->>W: Application request
    W->>S: Persist workflow + step plan
    W->>P: Evaluate requested operations
    P->>L: Persist policy decision
    alt Denied or approval required
        P-->>W: Decision; do not execute
        W->>S: Update blocked state
        W-->>A: Normalized outcome
    else Allowed
        P-->>W: Authorized operation scope
        W->>X: Dispatch authorized step
        X->>D: Typed operation request
        D-->>X: Typed operation result
        X->>L: Record execution outcome
        X-->>W: Normalized result
        W->>S: Persist step and workflow state
        W-->>A: Aggregated outcome
    end
    A->>S: Persist user-visible result
    A-->>I: Response envelope
    I-->>U: Render response
~~~

## 2. Workflow context is not shared mutable state

A workflow context contains:
- immutable request metadata and correlation identifiers;
- typed, bounded inputs;
- references to attachments and generated artifacts;
- prior step outputs explicitly declared as dependencies;
- deadline, cancellation and resource budget;
- policy decision and approval references;
- provenance and trust classification.

It does not contain:
- arbitrary Python objects from another package;
- provider clients or database connections;
- unrestricted environment variables or credentials;
- unbounded chat history or binary attachments;
- executable shell strings generated by a model.

## 3. Step contract

Every workflow step declares:
- stable operation identifier and contract version;
- input schema and output schema;
- dependencies on prior step outputs;
- required permissions and data-transfer classification;
- read-only or side-effect classification;
- timeout, payload and resource limits;
- idempotency behavior and cancellation support.

A step may only read declared dependency outputs. The coordinator validates the step result before exposing it to downstream steps.

## 4. Result envelope

~~~json
{
  "schema_version": "1.0",
  "request_id": "request-id",
  "workflow_id": "workflow-id",
  "step_id": "step-id",
  "status": "success",
  "data": {},
  "artifacts": [],
  "provenance": [],
  "error": null,
  "duration_ms": 0,
  "audit_ref": "event-id"
}
~~~

Allowed statuses distinguish success, partial, unavailable, invalid, denied, approval_required, cancelled, timeout, and failed. The exact enum belongs in the versioned contract package.

## 5. Example: repository review and security assessment

The user asks for a repository review. The coordinator builds a dependency graph:

~~~mermaid
flowchart TD
    A[Validate request and workspace scope]
    B[Load repository metadata]
    C[Read bounded source inventory]
    D[Static code review]
    E[Security assessment]
    F[Aggregate evidence and findings]
    G[Persist report and audit]
    H[Present findings]
    A --> B --> C
    C --> D
    C --> E
    D --> F
    E --> F
    F --> G --> H
~~~

The review and security steps do not call each other directly. They receive only the repository evidence they declared as input. The coordinator joins their outputs and preserves provenance. Any write, test execution, package installation, or Git mutation is a separate operation requiring its own policy and approval decision.

## 6. Failure and cancellation propagation

- Invalid request: reject before creating executable work.
- Missing capability/adapter: mark step unavailable; do not silently choose another operation.
- Policy denial: stop that operation and dependent steps that require it.
- Approval required: persist a pending state; resume only after a valid scoped approval.
- Timeout: mark the step timed out; do not automatically retry mutations.
- Cancellation: propagate to cancellable child steps and persist the final state.
- Partial output: keep it explicitly marked partial and allow only downstream steps that accept partial input.
- Audit persistence failure before protected execution: fail closed.
- Malformed or untrusted output: quarantine/reject; never interpret it as instructions.

## 7. Persistence boundaries

Workflow state and user session state are application data. Audit is a separate append-only record of decisions and outcomes. Large attachments and artifacts are stored outside the workflow context and passed by opaque, access-checked reference. Retention and deletion rules must apply consistently across all three stores.
